## 목적

디자이너가 *디자인 의도 외* prod 동작을 함께 바꾸는 사이드이펙트를 *차단·분리·기록*. *차단보다 분리·기록 우선* — 디자이너 흐름을 끊지 X. (c) 진짜 prod 영향만 명시 동의 + 자동 인계 큐 push.

## 발동 / 발동 X

- ✅ PreToolUse hook 경로 매치 (`hookSpecificOutput.permissionDecisionReason`에 `publishing-guard`)
- ✅ PostToolUse hook 패턴 매치 (`additionalContext`에 `publishing-guard` + `신호:` 목록)
- ✅ 디자이너 사전 자연어("이 파일 손대도 돼?")
- ❌ 디자이너 영역 안(`components/**` Tailwind class·CSS 변수·문자열 리터럴) → hook 자체가 신호 X
- ❌ `mock/**`·`lib/design-mode/**`·`asset/**`·`.env.kdesigner-design` → 허용, 침묵
- ❌ 디자인 토큰 변경(`tailwind.config`·`globals.css`) → `design-system-guard`

### §2. 변경 분류 (a) / (b) / (c)

훅에서 받은 *파일 경로* + *변경 신호*를 분류한다. *변경 위치 + 변경 종류* 함수 — 토글 유무가 아니다.

```
┌─────────────────────────────┬──────────────────────────────────┬────────────────────┐
│ (a) 격리 OK                  │ (b) 격리 부족                     │ (c) 진짜 prod 영향   │
├─────────────────────────────┼──────────────────────────────────┼────────────────────┤
│ lib/design-mode/**·mock/**  │ 디자인 모드 의도이나               │ props 시그니처 변경  │

│ Tailwind class·CSS 변수·    │ (토글 검사 없이                    │ 도메인 hook/store    │
│ 문자열 리터럴만 변경         │  process.env.<x> 분기 추가)       │ import 신규          │
│                             │                                  │ 상태 흐름 hook 신규  │
│ → 침묵·가벼운 인지            │ → 보강 제안 + AskUserQuestion 1회 │ <Link> 제거          │
│   동의 X·queue X            │   queue X                        │ 라우팅 메타 / 정리   │
│                             │                                  │ → 명시 동의 + queue  │
└─────────────────────────────┴──────────────────────────────────┴────────────────────┘
```

판정 핵심 신호: *시각 표현인가 데이터 흐름인가*. 시각 표현 = (a), 데이터 흐름 = (c). 애매하면 (b)로 묻기.

### §3. 응답 톤 (분류별 차별화) — *원칙만, 완성 문구·룩업 표 박지 X*

> 디자이너 친화 원칙: hook에서 받은 분류 토큰(`MATCHED_KIND`/`SIGNALS_KIND`)은 *Skill 내부 분류용*. 사용자 노출 응답은 *그때그때 파일·발화 맥락에 맞춰 자율 가공*. 케이스가 다양해 룩업 표로 다 못 잡으니, *원칙·금지 어휘·구조 요구·자가 점검*만 박고 구체 문구는 매번 생성.

**공통 원칙 4가지** (모든 응답에 포함):
1. *이 자리가 어떤 일을 하는 곳인지* — 디자이너 어휘(Figma 비유 가능 시) 1줄
2. *잘못 바뀌면 운영에서 어떤 사고가 생기나* — 구체 시나리오 1줄 (모호한 "문제 생길 수 있어요" X)
3. *그럼에도 진행해도 되는 이유* — "개발자가 자동으로 검토하는 목록에 기록되니 직접 판단 안 하셔도 돼요" 류 안심
4. *되돌리기 안전망* — "'방금 거 취소해줘' 한 마디로 되돌릴 수 있어요"

**(a) 격리 OK** — 짧고 가벼운 인지 1-2줄, 강제 X. 동의 X. 톤: *안심·가벼움*.

**(b) 격리 부족** — *보강 제안* + AskUserQuestion (1️⃣2️⃣3️⃣ + "잘 모르겠어요"):
- 1️⃣: 디자인 모드 전용 영역으로 옮기기 (안전·추천)
- 2️⃣: 그대로 두기 (이유 있어서)
- 3️⃣: 잘 모르겠어요 → 1️⃣ 권장
- queue push X

**(c) 진짜 prod 영향** — *명시 동의* + AskUserQuestion:
- 1️⃣: 의도한 변경 — 진행 + 개발자 검토 목록 자동 기록
- 2️⃣: 화면 확인용으로만 — 디자인 모드 전용으로 분리
- 3️⃣: 취소 — 손대지 않은 상태로 되돌리기
- "잘 모르겠어요"는 2️⃣ 권장
- 1️⃣ 선택 시 §5 queue push

> ⚠️ *완성 문구를 박지 마라* — 위 1️⃣2️⃣3️⃣의 *라벨*도 그대로 복붙용이 아닌 *의미*다. 사용자 발화·파일 맥락에 맞춰 자연스럽게 표현하라.

### §3.1 사고 시나리오 풀이 — *원칙만, 표 X*

hook 분류 토큰을 받아 *공통 원칙 2번 "운영에서 어떤 사고"*를 채울 때:

- **이 자리가 어떤 동작에 영향 주는 카테고리인지 추론** — 토큰명 자체에 힌트(`middleware` = 요청 가로채기, `api-route` = 서버 응답, `data-hooks` = 데이터 수신, `shared-state` = 화면 간 공유 정보, `props-signature` = 컴포넌트 사용 규칙). 토큰명이 처음 보는 형태면 *경로 + 변경 내용*에서 직접 유추.
- **그 카테고리에서 *디자이너 작업 맥락에서 가장 그럴 듯한 사고*를 1줄로** — 추상적 "문제 생김" X, "버튼이 다른 페이지로 가버릴 수 있음"·"빈 화면이 나올 수 있음" 같은 *시각 결과 어휘*
- **확신 없는 시나리오는 박지 X** — 차라리 "이 자리는 화면 모양 외 동작에도 영향을 줄 수 있어요. 어떤 의도로 바꾸시려는지 알려주시면 더 정확히 안내해드릴게요" 식 *질문으로 전환*

### §7. 자가 점검

응답 직전 체크:
- [ ] 분류 (a)/(b)/(c) 중 *하나만* (애매하면 (b))
- [ ] (c) 진행 동의 시 §5 queue push *실행*
- [ ] 응답 톤이 분류와 일치(가벼움/보강 제안/명시 동의)
- [ ] 디자이너 영역 안 변경엔 발동 X (오발 시 그대로 진행)
- [ ] 가드 패턴에 *특정 파일명·hash* 박지 않았는가 (범용 표현만)
- [ ] **사용자 노출 응답에 분류 라벨(`(a)/(b)/(c)`)·코드 용어(`prod`·`middleware`·`props 시그니처`·`hook`·`store`) 그대로 박지 않았는가**
- [ ] **(b)/(c) 응답에 1️⃣2️⃣3️⃣ 선택지가 포함**
- [ ] **응답 어딘가에 *되돌리기 안전망* 안내** ("'방금 거 취소해줘' 한 마디면 돼요")
